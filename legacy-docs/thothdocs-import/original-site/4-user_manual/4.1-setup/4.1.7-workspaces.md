# Workspace – Practical Guide

This section explains, in **non-technical** language, the role of the **Workspace** in ThothAI.

The goal is to clarify:

- **Why** the Workspace exists.
- **What** it contains and controls.
- **How** it links to SQL databases, vector databases, AI models and agents.
- **How** it affects the experience of a user asking natural language questions.

---

## 1 - What a Workspace is

A **Workspace** is the **working environment** where ThothAI performs searches for a specific business context.

You can imagine it as a **preconfigured combination** of:

- an **SQL database** (the actual data the queries will run on);
- the **vector database** associated with that SQL database (semantic memory: Evidence, Gold SQL, metadata);
- one or more **AI models** configured to generate and evaluate SQL;
- a set of **AI Agents** with different roles (question validation, SQL generation, testing, explanation, etc.);
- some **quality parameters** (number of tests, acceptance thresholds, selection strategies);
- the list of **users** allowed to use that Workspace.

When a user works in ThothAI (e.g. from the chat screen), **all questions** are interpreted and solved **within the selected Workspace**.

If no Workspace is selected, the system cannot decide:

- quale database interrogare,
- quali agenti attivare,
- quale contesto semantico usare.

For this reason, in the ThothAI frontend, **selecting a Workspace is mandatory** before sending questions.

---

## 2 - What a Workspace contains (conceptual view)

Internally the `Workspace` model links several components, but for a non-technical user it’s helpful to remember these associations:

### 2.1 - SQL database

Each Workspace is connected to an **SQL database** (`sql_db`):

- it holds the business data (sales, HR, production, etc.);
- all queries generated in the Workspace run **only** on this database;
- switching Workspace means changing the **entire data context**.

### 2.2 - Vector database

Through the SQL database, the Workspace also uses the **vector database** (`vector_db`) associated with that database.

This vector database contains:

- **Evidence** (interpretation phrases),
- **Gold SQL** (questions + validated queries),
- **metadata** on tables and columns.

When you ask a question in the Workspace, ThothAI queries the **dedicated vector DB** for that database, so that only the relevant context is used.

### 2.3 - Default AI model

Each Workspace has a **default AI model** (`default_model`), used to:

- translate natural-language questions into the technical language of the database;
- support agents that do not have a specific model assigned;
- keep the behavior within the Workspace consistent.

### 2.4 - Linked AI Agents

The Workspace links several specialized **AI agents**, for example:

- an agent that **validates** the question (`question_validator`),
- an agent that extracts **keywords** (`kw_sel_agent`),
- three agents for **SQL generation** at **BASIC**, **ADVANCED**, **EXPERT** levels (`sql_basic_agent`, `sql_advanced_agent`, `sql_expert_agent`),
- one or more agents for **test generation** (`test_gen_agent_1/2/3`),
- an agent to **evaluate the tests** (`test_evaluator_agent`),
- an agent that **explains SQL** in plain language (`explain_sql_agent`),
- an agent handling **human help requests** (`ask_human_help_agent`).

From a user perspective, it’s enough to know that:

- these agents work **sequentially and collaboratively** to check the question and generate quality SQL;
- everything that happens “behind the scenes” depends on the Workspace configuration you’re using.

### 2.5 - Quality and behavior parameters

The Workspace stores several parameters controlling **how deeply** ThothAI analyzes the problem, for example:

- **number of tests** to generate per question (`number_of_tests_to_generate`);
- **number of SQL** alternatives to produce internally before choosing the best one (`number_of_sql_to_generate`);
- **test acceptance threshold** (`evaluation_threshold`), expressed as a percentage;
- the **“Belt and Suspenders”** option (`belt_and_suspenders`), enabling an additional cautious selection of borderline queries through a dedicated evaluator.

You don’t need to know the technical details; it’s enough to remember that **Workspaces can differ** in how rigorous they are, and these settings influence:

- answer reliability,
- processing time,
- how “cautious” the SQL selection is.

## 3 - Workspace, users, and permissions

A Workspace is not visible to every user by default. Internally:

- each Workspace links to **one or more users** (`users`);
- a single user can have **access to multiple Workspaces**;
- some Workspaces can be marked as **default** for a user (`default_workspace`).

### 3.1 - Who sees what

When a user opens the ThothAI frontend:

- the available Workspace list is filtered by user;
- the system looks for a **default Workspace** for that user;
- if it exists, it is proposed as the initial Workspace.

In addition, based on **Groups** and **Group Profiles** (configured in the authentication section):

- some users see only the natural-language explanation;
- others can view the generated SQL as well;
- power users may access more Workspaces or higher-level Workspaces.

### 3.2 - Default Workspace

The concept of a default Workspace matters because:

- at **first login**, ThothAI automatically selects the Workspace marked as default for the user;
- if no default exists, the **first available Workspace** is chosen;
- this initial choice is remembered by the frontend, so you don’t have to repeat it every time.

For the end user, this means that, after the first setup by the admin, selecting a Workspace manually is often unnecessary.

---

## 4 - Workspace levels: BASIC, ADVANCED, EXPERT

Every Workspace has a **functionality level** (`level`):

- **BASIC**
- **ADVANCED**
- **EXPERT**

These levels help the frontend select the **SQL generation strategy**.

In practical terms:

- **BASIC**: simpler, less aggressive approach, suitable for standard logic.
- **ADVANCED**: uses more sophisticated generation logic, taking more context into account.
- **EXPERT**: enables the “expert” agent and more complex strategies for advanced scenarios.

The level doesn’t change your permissions, but it **modifies how the models and agents behave**, influencing the type of SQL produced.

---

## 5 - How the Workspace drives the Text-to-SQL flow

When you send a question from the chat screen:

1. the frontend checks whether you **selected a Workspace**;
2. if not, it shows an error (e.g., *"No workspace selected"* and the action *"Please select a workspace from the sidebar"*);
3. if a Workspace is selected, its **ID and parameters** are passed to the SQL generation service;
4. the service configures all **AI Agents** using that Workspace’s settings (default model, agents, number of tests, thresholds, etc.);
5. the question is processed **within the SQL + vector DB context** associated with the Workspace.

In short, the Workspace is the **entry point** that tells ThothAI “where to look” and “how to reason” to answer your question.

---

## 6 - Preprocessing and Workspace statuses

For best results, a Workspace often needs to be **preprocessed** from the admin area.

During preprocessing, ThothAI:

- analyzes the **SQL database schema** (tables, columns, relationships);
- generates or updates **table/column descriptions**;
- loads or updates the **vector database** with the necessary information (metadata, Evidence, Gold SQL);
- optionally generates or updates **AI comments** for tables and columns.

The Workspace model contains multiple **status fields** indicating what is happening, for example:

- overall preprocessing status (`preprocessing_status` – *IDLE*, *RUNNING*, *COMPLETED*, *FAILED*);
- status of table/column comment generation (`table_comment_status`, `column_comment_status`);
- timestamps of the last runs (`last_preprocess`, `last_evidence_load`, `last_sql_loaded`).

Users should know:

- if preprocessing **failed** or never ran, answer quality may be limited;
- in test environments or after major schema updates, you may need the admin to **rerun preprocessing** for that Workspace.

---

## 7 - Selecting and changing Workspaces in the UI

In the ThothAI frontend, the Workspace is managed via a **sidebar selector**.

Typical behavior:

- on login, the system tries to set the user’s **default Workspace**;
- if no default exists, the first available Workspace in the list is selected;
- the user can switch Workspaces at any time from the dropdown.

Additionally, the frontend **remembers** your last choice locally, so the next session starts with the same Workspace (if still available).

Remember that **every question** is interpreted relative to the currently selected Workspace. If you’re handling multiple business contexts (e.g., HR and Sales), verify you’re in the right Workspace before asking new questions.

---

## 8 - Workspace diagnostics (DB and Vector DB connection)

For some Workspaces, especially in non-Docker environments, it can be useful to verify that:

- the **SQL database** is reachable;
- the **vector database** is configured and accessible;
- the **embedding service** (model + API keys) is correctly set.

In the frontend, there is a **diagnostics** section tied to the Workspace, allowing you to:

- run a **connection test** to the Workspace’s vector database;
- view key configuration info for the Vector DB (provider, embedding model, host, port, collection name);
- check whether the required **embedding API key** is present.

If the tests fail, it signals that:

- the vector database isn’t configured correctly;
- the service isn’t reachable from ThothAI;
- embedding keys are missing or incorrect.

In those cases, involve the technical team or whoever manages the ThothAI installation.

---

## 9 - Common Workspace-related errors

Certain error messages or unusual behaviors are directly related to the Workspace, for example:

- chat message stating **"No workspace selected"**, asking you to pick one from the sidebar;
- preprocessing stuck in **FAILED** state for a Workspace;
- vector DB connection tests returning errors;
- irrelevant answers after switching Workspaces (e.g., asking HR questions while still in the Sales Workspace).

In such cases, always check:

- that you selected the **correct Workspace**;
- that the Workspace is **fully configured** (SQL DB, vector DB, agents, settings);
- that no preprocessing tasks are in progress that might temporarily restrict usage.

---

## 10 - Summary

- The **Workspace** is the primary unit for configuring ThothAI’s working context.
- Each Workspace links **an SQL database**, its **vector database**, one or more **AI models**, and a set of **agents** cooperating to generate and evaluate SQL.
- Users only access Workspaces assigned to them, and may have a **default Workspace**.
- Workspace level (BASIC / ADVANCED / EXPERT) affects the **SQL generation strategy**.
- Parameters such as number of tests, generated SQL candidates, and thresholds govern answer **quality** and caution.
- Preprocessing populates the vector database and updates the metadata necessary for quality results.
- If you don’t select a Workspace or it’s misconfigured, ThothAI cannot respond properly to natural-language questions.
