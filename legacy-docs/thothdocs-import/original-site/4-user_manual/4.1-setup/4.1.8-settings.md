# Settings – guida pratica

This section describes, in **non-technical** language, the role of **Settings** in ThothAI.

Settings are not tied to permissions or security, but they control **how** the system:

- searches for similarities between texts (LSH similarity);
- decides when to use **schema linking**;
- handles preprocessing parameters and vector-database retrieval rules.

---

## 1 - What Settings are

A **Setting** object represents a reusable **technical configuration profile**.

Practically speaking:

- a Setting contains the parameters that influence **how ThothAI prepares and uses context**;
- the same Setting can be **reused by multiple Workspaces**;
- each Workspace can be linked to **only one Setting** (`workspace.setting`).

While the Workspace defines *where* you work (databases, agents, models, users), the Setting defines **how** the system performs internal similarity and schema-linking operations.

---

## 2 - Relationship between Settings and Workspaces

In the internal model, every Workspace has a `setting` field pointing to a **Setting** object.

This means:

- two different Workspaces can **share the same Setting** (e.g. if they use the same similarity strategy);
- or each Workspace can have a **dedicated Setting** if different policies are required.

During **preprocessing** and answer generation, ThothAI reads the parameters from the Workspace’s Setting to decide, for example:

- how many examples to consider;
- how tolerant to be with text similarity;
- when to activate schema linking on tables.

If a Workspace has no Setting configured, some operations (like advanced preprocessing) cannot run correctly.

---

## 3 - Similarity parameters (LSH)

An important portion of Settings deals with **similarity search** based on LSH (Locality-Sensitive Hashing).

Without diving into mathematical detail, think of it this way:

- ThothAI turns text (column names, descriptions, sample values) into compact **fingerprints**;
- these fingerprints make it fast to find **similar** text;
- LSH parameters control **how similar** two elements must be to be considered relevant.

Key fields include:

- **signature_size**: size of the “fingerprint” used to compare text.
  - larger values = more detail and accuracy, but potentially higher cost;
- **n_grams**: length of the text fragments (n-grams) used to build the fingerprint.
  - this sets how fine the text segmentation is;
- **threshold**: minimum similarity to consider two elements “close enough.”
  - higher threshold = more selective (less noise, higher risk of missing something);
  - lower threshold = more permissive (more results, more noise).

Other helpful LSH parameters:

- **lsh_top_n**: how many top results to keep from the LSH search;
- **edit_distance_threshold**: acceptable edit distance while still considering two texts similar;
- **embedding_similarity_threshold**: minimum embedding similarity required to accept a result.

For non-technical users it’s enough to know:

- these values determine **how many pieces of evidence** are considered “similar”;
- noisy environments (many columns/texts) benefit from **higher thresholds** or lower `lsh_top_n`;
- small or homogeneous environments can use more permissive values.

---

## 4 - Schema linking: when it activates

**Schema linking** helps ThothAI decide **which schema parts** (tables/columns) to include in the question context, considering both the number of columns and the model’s maximum context window.

Settings control this logic with two main parameters:

- **max_columns_before_schema_linking**
  - maximum column count before schema linking becomes **mandatory**;
  - if the DB exceeds this threshold, ThothAI forces a strategy that selects only relevant portions;

- **max_context_usage_before_linking**
  - maximum percentage of the model’s **context window** that the schema can occupy;
  - if the raw schema would exceed this percentage, the system trims it via schema linking.

Practically:

- on **small databases** these limits might never be hit, so the schema is passed almost entirely;
- on **very large databases** (tens of thousands of columns) these parameters are crucial to keep requests manageable and avoid context overflow.

---

## 5 - Other control parameters

Beyond the main parameters, Settings include other fine-tuning fields:

- **max_examples_per_column**: maximum number of sample values kept per column
  - too many = richer context but heavier payload;
  - too few = lighter context but less representative;
- **verbose**: enables a more “verbose” LSH preprocessing mode (more logs/details);
- **use_value_description**: whether to leverage value descriptions (beyond column names) to improve similarity.

These parameters are usually managed by the **technical team** or whoever handles data engineering. Business users typically don’t adjust them, but it’s useful to know they exist and can be tuned to match the database’s characteristics.

---

## 6 - When Setting changes take effect

Changing a Setting does not instantly affect ThothAI’s behavior on already preprocessed data.

In general:

- Setting parameters are read during **preprocessing** and certain **schema-selection** phases;
- after modifying a Setting used by one or more Workspaces, it’s often best to **rerun preprocessing** so that:
  - the new similarity thresholds rebuild the fingerprints;
  - schema handling and examples align with the new configuration.

In test environments you often run multiple cycles:

1. tweak the Settings slightly;
2. rerun preprocessing;
3. observe whether answer quality (or timing) improves.

---

## 7 - Who should modify Settings

Settings are intended to be configured primarily by:

- ThothAI **technical administrators**;
- **data engineers** or **data scientists** familiar with data volumes/characteristics;
- people responsible for **installation** and performance tuning.

For business users it’s enough to know:

- there is usually a default Setting (often named *"Default"*);
- the admin team assigns Workspaces to specific Settings;
- performance or relevance issues may require **adjusting Settings**, not the Workspace itself.

---

## 8 - Common Setting-related issues

Common issues caused by misconfigured Settings include:

- **missing default Setting** required by automated scripts/processes;
- **thresholds too low**, generating noisy results (too many matches);
- **thresholds too high**, hiding matches that would be useful;
- `max_columns_before_schema_linking` / `max_context_usage_before_linking` limits unsuitable for your DB (e.g. too low for large warehouses).

When these issues occur, involve someone with ThothAI technical expertise to:

- review the Settings;
- realign Workspaces to a more suitable profile;
- rerun Workspace preprocessing if needed.

---

## 9 - Summary

- **Settings** are reusable technical profiles controlling **similarity**, **schema linking**, and certain preprocessing choices.
- Each Workspace points to a Setting, and multiple Workspaces can share the same profile.
- LSH parameters (signature size, similarity thresholds, top results, per-column examples) affect how many and which elements are deemed “similar.”
- Schema-linking parameters decide when to **shrink** the schema passed to the model, especially in large contexts.
- Changes to Settings often require **rerunning preprocessing** to take full effect.
- Typically, the technical team manages Settings; business users mainly interact with Workspaces already tied to the appropriate profiles.
